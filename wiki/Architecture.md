# 架构

## 三个进程，一个大脑

```
┌────────── 驿 · Yi.app（Swift + WKWebView，只负责显示）──────────┐
│   连接            机器            设置                          │
└──────────────────────────┬──────────────────────────────────────┘
                           │ HTTP + SSE，仅监听 127.0.0.1
┌──────────────────────────▼──────────────────────────────────────┐
│  agent.py（Python 3.12，零第三方依赖）——唯一的大脑               │
│    ├── 生命周期：创建 / 销毁 / 竞价回收自愈                       │
│    ├── 调和循环：把实际状态收敛到期望状态                         │
│    └── 事件流：状态一变立刻推给界面                               │
└──────────────────────────┬──────────────────────────────────────┘
                           │
         ┌─────────────────┴──────────────────┐
         ▼                                    ▼
  阿里云 ECS（香港 · 竞价）            mihomo 内核（本地代理）
```

**界面里没有一行网络逻辑。** 所有判断都在 agent 里做，界面只是"把状态画出来、
把点击传回去"。这样重开窗口、换界面都不会影响正在跑的连接。

## 状态的唯一来源

早期版本的 CLI、agent、界面各算一套状态，自然会互相矛盾
（界面说"已连接"、CLI 说"没连"）。现在只有一个 `status.snapshot()`，
输出 8 个状态之一：

```
no_machine → busy → installing → ready → connected
                        ↓           ↓
                 install_failed   degraded
                        ↑
                    reclaimed
```

优先级是刻意定的：`busy > reclaimed > install_failed > installing > connected >
degraded > ready > no_machine`。**正在忙**永远压过一切——
因为你此刻最需要知道的是"它在干活"，而不是"上一次的状态"。

## 期望状态 + 调和循环（这个项目最值钱的部分）

界面上的连接开关写的不是"现在去连"，而是**期望状态** `want_connected`。
每 8 秒，调和循环把实际状态往期望状态收敛：

| 出了什么事 | 调和循环的反应 |
|---|---|
| 代理内核崩了 | 重新拉起来 |
| 服务端换了 IP（竞价回收后重建） | 用新地址重写配置并重载 |
| 系统代理被别的程序关掉了 | 再打开 |
| 内核起不来 | **把系统代理关掉**，回退直连（绝不指向死端口） |

**升级安全**：老版本配置里没有 `want_connected` 这个键。这时以
"内核是不是在跑"为准——否则一次升级就会把正在用的连接掐掉。

## 为什么不自己实现协议

代理协议（VLESS / REALITY 握手 / XTLS）的细节多到可以吃掉整个项目，
而且写错了是**静默的**：能连上不代表安全。

所以：客户端内核用 [mihomo](https://github.com/MetaCubeX/mihomo)，
服务端用 [Xray-core](https://github.com/XTLS/Xray-core)。
本项目只负责"生成配置、拉起内核、开关系统代理、校验出口"。

## 为什么是竞价实例

香港按量付费 ECS 一小时几毛到一块多；竞价实例（抢占式）通常是一到两折。
代价是**随时可能被回收**——而这个项目就是围绕这个代价设计的：
凭据复用 + 自动重建 + 调和循环，把"随时会没"变成一个你几乎感觉不到的事件。
