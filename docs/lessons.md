# 踩坑记录

这些不是"可能遇到的问题"，是真机上**真实撞到并修掉**的。每条都附根因，
大部分还配了回归测试。留着是因为：它们代表了这类系统真正的难点。

## 一、真实世界不守约

### 1. 阿里云会把回收的 IP 再分配出去

**现象**：`yi up` 卡在"等待服务端就绪"直到超时（实测 8 分钟），而机器其实早就装好了。

**根因**：这个 IP 之前是**别人**的机器用的（阿里云回收后重新分配给了我们），
而旧主机密钥还留在
`known_hosts` 里。`StrictHostKeyChecking=accept-new` 对**变更过的密钥是拒绝的**
（这本身没错，防 MITM），但对我们自己刚建的实例就成了假警报：SSH 每次失败并重试。

**修法**：识别该错误 → 从 `known_hosts` 删掉那一条 → 重试一次。
回归测试见 `tests/test_ssh_hostkey.py`。

### 2. 同一个实例，不同接入点给出不同答案

**现象**：按实例 ID 过滤查不到，裸列表却查得到；`DeleteInstance` 报"实例不存在"，
但实例明明在列表里、还在计费。

**根因**：阿里云不同 POP 之间数据不一致（报错信息里能看到 `from POP`）。

**修法**：

- 判断"资源还在不在"只用**裸列表 + 本地过滤**，不用带过滤条件的查询
- `DescribeInstanceStatus` **不能拿来做决策**：它可能忽略过滤条件、返回别的实例的状态
- 判定"已消失"必须**连续 2~3 次**确认；`DeleteInstance` 报 NotFound 也不能直接当成功

回归测试：`tests/test_reconcile.py`、`tests/test_ecs_request.py::DeleteRetryTests`。

### 3. 用旧接口建 VPC 实例，有时会建成"停止态且没有公网 IP"

**现象**：实例创建成功，5 秒后变成 `Stopped`（停止模式 KeepCharging），
`PublicIpAddress` 是空的。手动 `StartInstance` 之后 10 秒就正常。

**根因**：`CreateInstance`（竞价唯一可用的接口）在 VPC 下不保证自动分配公网 IP，
偶尔会以停止态落库。竞价和按量付费都复现过。

**修法**：`ensure_running()`（是 Stopped 就显式启动）+ `ensure_public_ip()`
（没有就 `AllocatePublicIpAddress`）。

**教训**：失败模式不一定是"报错"，也可能是"成功了一个半成品"。

## 二、我方代码的锅

### 4. 静默降级一个安全属性 = 埋雷

**现象**：配置里写着 `spot_duration = 1`（买 1 小时保护期），但代码发现阿里云不接受
`SpotAsPriceGo` + 保护期，就**静默忽略**了保护期，只在日志里打一行。
结果买到的机器 6 秒后就被回收了。

**修法**：参数冲突要么报错让用户选，要么按**更安全**的一侧升级并显式说明。
现在"要保护期"直接蕴含"用限价策略"，出价自动按市场价峰值 × 1.5 计算。

**教训**：日志里那句"已忽略 X"，往往就是下一次故障的预告。

### 5. `resolve_port()` 分不清"别人占的"和"自己内核占的"

**现象**：连接之后，**整台机器的浏览器都上不了网**。

**根因**：同一次启动里 `resolve_port()` 被调用了两次。第一次把内核起在 7898；
第二次把**内核自己占的 7898** 当成"端口冲突"，换成 7899，然后系统代理被指向
7899 这个没人监听的端口。日志就是这三行：

```
端口 7897 已被占用 → 改用 7898
mihomo 已就绪，混合端口 7898
端口 7898 已被占用 → 改用 7899        ← 它把自己当成别人了
系统代理已开启（端口 7899）
```

**修法**（四层，每层单独都够挡住）：

1. 内核在跑时**直接用它记录的端口**，绝不再探测
2. `set_system_proxy(on)` 里加硬保险：**端口没在监听就拒绝设置**
3. 内核起不来时**把系统代理关掉**（fail-open 回直连），而不是把用户挂在死端口上
4. 状态接口报**实际端口**，不是写死的默认值

回归测试：`tests/test_reconcile.py::PortTests`。

**教训**：这类 bug 的代价是**用户整台机器断网**，且很难查——
所以要有前置硬保险，而不是事后补救。

### 6. 改动了 DOM 却没同步改 JS 引用（两次）

**现象**：界面停在"正在读取状态…"，点什么都没反应。

**根因**：

- 第一次：同一作用域里声明了两次 `const sub`，**语法错误导致整个脚本不执行**
- 第二次：把 header 的状态点换成图标，但 `render()` 还在给 `$("dot")` 赋值，
  每 3 秒一次 TypeError，渲染在那一行中断

**修法**：打包时检查界面脚本语法；`render()` 里所有元素访问走 `need()`
（元素缺失返回哑对象），一处缺失不再拖垮整页。

**教训**：**GUI 的失败模式是"静默中断"**——不是局部出错，是后面全部不执行。
单元测试对此完全无感，必须真的有办法看到界面（我们用 playwright 截图）。

### 7. 批量改名把启动器改成了自己

**现象**：`./yi status` 卡死，但 `ps` 看起来完全正常（进程数一直是 1）。

**根因**：批量替换 `s/\bvpnctl\b/yi/g` 把别名脚本里的 `exec "$HERE/vpnctl"`
改成了 `exec "$HERE/yi"`——**自己 exec 自己，无限循环**。

**教训**：改名脚本要排除"自身就是目标名"的文件；改完立刻手工验证入口脚本。

### 8. 本机装过包，掩盖了"装进 App 之后找不到包"

**现象**：CI 的打包校验红了，报 `ModuleNotFoundError: No module named 'yi'`；本机同样的
检查却是绿的。

**根因**：`app/agent.py` 按源码布局找包（`dirname(HERE)/src`）。但打进 App 之后，
`agent.py` 和 `src/` 是**同级**的（都在 `Contents/Resources/` 下），路径就差一级。

本机测不出来，是因为开发机上跑过 `pip install -e .`——`import yi` 永远成功，
把"路径算错了"这件事盖得严严实实。**验证环境和真实环境有一个变量不同，
验证就等于没做。**

**修法**：`_locate_package_root()` 两种布局都试，谁在就用谁。
回归测试 `tests/test_app_bundle.py` 用 `python -S`（禁用 site-packages）
起子进程——一个真正看不见已安装 `yi` 的解释器。**没有 `-S` 的话，这个测试
会永远是绿的。**

**教训**：凡是"打包/部署之后才成立"的路径假设，都要在**没有开发环境加持**的
解释器里测一遍。同理，CI 存在的价值就在这里——它是唯一一个没有你本机那些
历史包袱的环境。

### 9. 一个"失败也不是错误"的功能，会安静地什么都不做

**现象**：接上社区分流规则集之后，`RULE-SET` 那几行在配置里明明写着，
实际却一条都没生效，而且**没有任何报错**。

**根因**：mihomo 对规则集的处理是"尽力而为"——下载失败就留空，内核照常启动。
所以从"机器买好"到"人觉得没问题"之间，没有任何一步会报错。

这是设计得好的一面（规则集挂了不会导致用户断网），但代价是**故障完全静默**：
用户只会觉得"某些网站走了代理、有些没走，说不清为什么"。

**修法**：这类"降级而非失败"的功能必须自己对外报状态。于是有了 `./yi rules`
（每个集合多少条、什么时候更新的）和内置基础规则始终保留当保险。

**教训**：**一个不会失败的功能，也不会告诉你它没工作。** 判断一个特性是否
需要状态上报，就看它失败时用户能不能自己发现——不能的话，就得替他盯着。

### 10. 一次"更新规则集"把用户的网弄断了，还顺带牵出两个更贵的 bug

**现象**：跑完 `yi rules --update` 之后，用户正在用的代理端口没人在监听了。
系统代理还指着那个端口 —— 网断了。

**根因（我写的）**：重新生成内核配置时用了函数签名的默认端口 `7897`，
而不是这台机器**正在用的** `7899`。重载配置后内核换到 7897 去监听，
系统代理还指着 7899。

顺着这条线查下去，发现两个更贵的问题：

1. **进程活着 ≠ 在服务**。调和循环只检查 `running_pid()`，不看端口是否真的
   在监听。所以"内核在跑但没在监听"这种状态，它认为一切正常，什么都不做 ——
   而用户的网正断着。现在调和循环会真的探一次端口，不对就重启。
2. **网络错误被当成了"实例被回收"**。看门狗里，API 调用失败后 `present`
   仍是 `None`，于是计入"查不到"的次数，两次就触发**重建机器**。
   API 抖两下，用户白花一笔钱、IP 白换一次。

而之所以会出现"API 调用失败"，是因为第三个问题：

3. **阿里云的控制面请求走了系统代理**。urllib 默认读取 macOS 系统代理设置
   并**缓存**在默认 opener 里，于是本地代理一停，所有 API 调用变成
   `ECONNREFUSED` —— 正好喂给上面那个误判。

**教训**：

- **默认参数是给"没人在用"的场景准备的。** 凡是"重新生成/重新应用"的操作，
  参数必须来自**当前实际状态**，不能来自函数签名。这个 bug 的本质是
  "把默认值当成了当前值"。
- **健康检查要检查"能不能干活"，不是"进程在不在"。**
- **不确定 ≠ 否定。** 查不到和不存在是两件事，把它们合并计数，代价是
  真金白银。
- **控制面流量不要走数据面代理。** 两者可用性应该是独立的：代理挂了，
  你仍然要能通过 API 把机器管好——那正是你最需要它的时刻。

## 三、CSS 陷阱

### 10. 通用悬停把主按钮的渐变盖掉了

```css
button.btn:hover:not(:disabled) { background: var(--surface-3); }  /* 通用悬停 */
button.btn.primary { background: linear-gradient(...绿...); }     /* 主按钮 */
```

`:not(:disabled)` 里的伪类**会算进选择器权重**，所以"通用悬停"反而比 `.btn.primary`
更 specific：一悬停，绿色渐变被深灰覆盖，**但投影还是绿的**，
于是出现"深灰按钮 + 底部一道绿光"的怪样子。

**修法**：变体必须把自己的所有状态（`:hover` / `:active` / `:disabled`）补全。

**规律**：通用态里只要带 `:hover` 或 `:not()`，就会反超只有一个修饰类的规则。

## 从这些坑里长出来的工程约定

1. **测试先行**：每个真机 bug 的修复都要配一个回归测试
2. **不静默降级安全属性**
3. **不相信单次 API 返回**：判断资源消失要连续多次确认
4. **不写"点一下做一串动作"**：用期望状态 + 调和循环
5. **前置硬保险 > 事后补救**（例如"端口没监听就拒绝设置系统代理"）
6. **GUI 必须真的看到**：改完界面就用 playwright 走一遍
7. **日志要落盘**：用户终端回滚抓不到，`~/.config/yi/logs/` 是唯一的线索
